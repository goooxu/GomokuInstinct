# 第 11 章　静默失败图鉴

## 11.1 一类特别难缠的 bug

先给个定义。这一章讲的 bug 有三个共同点：

1. **不抛异常、不崩溃、不产生 NaN**；
2. **测试不会变红**（因为没人想到要为它写测试）；
3. **表现出来就是"效果差一点"或者"慢一点"** —— 而这两件事在深度学习项目里
   永远有一百个别的解释。

普通 bug 会告诉你它在哪。这类不会。你会去调超参、换结构、加数据，
花几天时间优化一个根本不是瓶颈的东西。

这个项目里至少撞上了十五次。下面是完整清单。

### #6　trainer 空转 3 小时 37 分

**症状**：训练在跑，GPU 有负载，日志在输出，一切正常。但 step 数几个小时没怎么涨。

**根因**：trainer 扫描 actor 写的分片时，用的是

```python
if f.split("_")[0] in ("actor",):     # 想匹配 actor0_000123.npz
```

而实际文件名是 `actor0_000123.npz`，`split("_")[0]` 得到的是 `"actor0"`，
**不等于 `"actor"`**。于是 trainer 一个新分片都没吃进去，只能反复训练回放池里的旧数据。

**为什么没被发现**：因为它不报错。回放池里有数据（启动时从磁盘恢复的），
训练照常进行，loss 照常下降 —— 它在过拟合那批旧数据。

**修法**：改成 `startswith`，补一条回归测试，并加了一条**空闲告警** ——
超过 `idle_warn_seconds` 没有吃进新数据就打日志。

**教训**：字符串匹配是静默失败的重灾区。任何"扫描目录找文件"的代码，
都要有"一直没找到"的告警。

### #8　给样本加了一个字段，25 万局数据作废

**症状**：加了 `blunder_gap` 字段之后重启训练，一切正常，就是失误挖掘一直没生效。

**根因**：分片读取按字段名硬取：

```python
data = {name: shard[name] for name in _FIELDS}    # 旧分片里没有 blunder_gap
```

旧分片抛 `KeyError`，而外层有个宽泛的 `except` 把它吞了 —— 于是**磁盘上已有的
25 万局数据全部被静默跳过**。

**修法**：`_read_shard()` 对缺失字段填零，并**明确报告跳过了多少**。

**教训**：数据格式演进必须显式处理向后兼容。"新字段"这种改动看起来无害，
恰恰因为无害才没人去检查它对旧数据的影响。

### #9　未训练的价值头 + 认输 = 数据污染

**症状**：正式训练一开跑，黑白胜率就极度失衡。

**根因**：自博弈开了**认输**机制 —— 价值估计低于 `-0.92` 就判负，省下后半盘的算力。
这在成熟模型上是标准做法。但训练最开始时，价值头是**随机初始化**的，
它的输出跟局面毫无关系。于是大量本可以继续的对局被随机地判负，
**训练数据里被灌进了一批错误的胜负标签**。

**怎么确认的**：做了一次受控 A/B —— 同样的种子、同样的配置，只改认输开关。

这里有个我自己的错误值得记下来：确认之前，我已经把"认输导致失衡"这个**未经验证的
因果结论**写进了配置注释。后来去核对 M3 的基准数据，发现那次**也开着认输**，
因果关系并不成立。结论要么改掉，要么做实验 —— 不能因为"听起来很有道理"就写下来。

**修法**：训练初期关闭认输，等价值头有判断力了再开。

### #11　永远开不出白棋局

**症状**：网页版里选"我执白"，点新局，开出来还是黑棋。必现。

**根因**：请求发出前会先 `render()` 一次刷新界面，而 `render()` 里有一句把颜色下拉框
**回写成当前对局的颜色**。等真正去读用户选的值时，"白"已经被覆盖回"黑"了。

```python
guard(fn):
    pending = True
    render()          # ← 这里把 $("color").value 重置了
    setState(await fn())   # ← fn 才去读 $("color").value
```

**根子**：**把一个输入控件当成状态显示去写**。

**为什么没被发现**：服务端 `/api/new {color:"white"}` 的测试一直是通过的。
bug 全在浏览器那一侧，而容器里没有 JS 运行时，前端没有任何自动化覆盖。

**修法**：`render()` 不再碰任何输入控件。另外用纯 Python 的 esprima 做 JS 语法检查
（语法错误的后果是整页白屏，服务端却一切正常），并把"`render()` 里不得给输入控件赋值"
写成静态不变量检查。

**教训**：**覆盖缺口不会因为你没想到就不存在**。这个项目的前端至今没有运行时测试，
这是一个真实存在的空洞，只能靠人工点。

### #15　指标变好，恰恰是因为坏了

**症状**：step 15,600~15,750 这 150 步里，top1 一致率冲到 0.778、价值准确率 0.904、
超出量掉到 0.308 —— **三项全是整个训练的最佳值**。然后一步回落到 0.630 / 0.770 / 0.562，
比出事之前还差。

**根因**：trainer 在 step 15,588 重启，内存里的回放池归零。`min_positions_to_start`
这道门槛是 **50,000 条的绝对值**，而回放池容量是 400 万 —— 于是只攒到 51,326 条
（容量的 1.25%）就开训，网络迅速过拟合那一小撮样本。指标衡量的是"拟合当前池子有多好"，
池子小到 1/80，指标当然好看。

**为什么危险**：这是本章里唯一一个**让指标变好**的 bug。前十四个至少还表现为"变差"或
"不动"，这个反过来 —— 如果你恰好在那一刻截图、或者用单点最优值写进报告，
就会把一次故障当成突破。（我差点就这么干了，见第 12 章那段更正。）

**怎么防**：门槛不该是绝对值，应当要求回放池恢复到容量的某个比例再开训。未做。
完整证据见[附录](appendix-training-run.md) A.7。

## 11.3 四种应对手段

十五个 bug 里没有一个是靠"仔细读代码"发现的。有效的是下面四种做法。

### ① 审计计数器：给不可见的东西装一个指针

凡是"可能悄悄退化"的机制，都给它一个能看见的数字：

| 机制 | 计数器 | 它变成什么样意味着出事了 |
|---|---|---|
| 三三递归判定 | 实际最大深度 / 封顶次数 | 封顶次数 > 0 → 判定退化成近似 |
| Kahan 补偿 | `optim/compensation_norm` | 掉到 0 → 补偿没生效 |
| 数据供给 | `buffer/reuse` | 飙高 → 自博弈跟不上，在过拟合 |
| 分片摄入 | 空闲告警 | 长时间没吃到新数据 → 扫描逻辑坏了 |

**这些计数器要写进验收条件，不是写进日志就完事。** 递归深度那条被写成
"封顶次数必须为 0"，才真正拦住了问题。

### ② 双实现差分：同一个规范，两种做法

规则引擎写了两遍（第 2 章）。同一个人用同一种思路写两遍会犯同样的错，
所以两份实现的**做法必须不同** —— 一份逐格扫描，一份位掩码运算。

再加一条**与实现无关**的性质检查（八重对称不变性），能抓出两份实现都错的情况。

### ③ 对照实验，而不是推理

"认输导致数据污染"这个结论，是靠固定种子的 A/B 实验确认的，不是靠想。
"每请求新线程重建 cuBLAS 句柄"是靠逐层计时确认的，中间还排除了两个听起来很合理的
错误假设。

**听起来有道理的因果，写进文档之前要先做实验。** 否则你会像我一样，
把一个未经验证的结论写进配置注释，几天后才发现它不成立。

### ④ 把发现的每个坑写成回归测试

图鉴里的每一条，现在都有对应的测试或自动检测。这不是仪式感 ——
这类 bug 的特点就是"改对了以后看不出区别"，没有测试，下一次重构就会把它改回去。

举个例子：第 6 章那条"随机落子时禁手告负率必须 > 0"的测试。
它看起来是在测一件废话，实际上它锁住了"禁手点仍是合法落子"这条语义 ——
如果哪天有人顺手在 runner 里加了禁手屏蔽，这条测试会红，而所有别的测试都不会。
