# 第 11 章　静默失败图鉴

## 11.1 一类特别难缠的 bug

先给个定义。这一章讲的 bug 有三个共同点：

1. **不抛异常、不崩溃、不产生 NaN**；
2. **测试不会变红**（因为没人想到要为它写测试）；
3. **表现出来就是"效果差一点"或者"慢一点"** —— 而这两件事在深度学习项目里
   永远有一百个别的解释。

普通 bug 会告诉你它在哪。这类不会。你会去调超参、换结构、加数据，
花几天时间优化一个根本不是瓶颈的东西。

这个项目里至少撞上了十九次。下面是完整清单。

### #6　trainer 空转 3 小时 37 分

**症状**：训练在跑，GPU 有负载，日志在输出，一切正常。但 step 数几个小时没怎么涨。

**根因**：trainer 扫描 actor 写的分片时，用的是

```python
if f.split("_")[0] in ("actor",):     # 想匹配 actor0_000123.npz
```

而实际文件名是 `actor0_000123.npz`，`split("_")[0]` 得到的是 `"actor0"`，
**不等于 `"actor"`**。于是 trainer 一个新分片都没吃进去，只能反复训练回放池里的旧数据。

**为什么没被发现**：因为它不报错。回放池里有数据（启动时从磁盘恢复的），
训练照常进行，loss 照常下降 —— 它在过拟合那批旧数据。

**修法**：改成 `startswith`，补一条回归测试，并加了一条**空闲告警** ——
超过 `idle_warn_seconds` 没有吃进新数据就打日志。

**教训**：字符串匹配是静默失败的重灾区。任何"扫描目录找文件"的代码，
都要有"一直没找到"的告警。

### #8　给样本加了一个字段，25 万局数据作废

**症状**：加了 `blunder_gap` 字段之后重启训练，一切正常，就是失误挖掘一直没生效。

**根因**：分片读取按字段名硬取：

```python
data = {name: shard[name] for name in _FIELDS}    # 旧分片里没有 blunder_gap
```

旧分片抛 `KeyError`，而外层有个宽泛的 `except` 把它吞了 —— 于是**磁盘上已有的
25 万局数据全部被静默跳过**。

**修法**：`_read_shard()` 对缺失字段填零，并**明确报告跳过了多少**。

**教训**：数据格式演进必须显式处理向后兼容。"新字段"这种改动看起来无害，
恰恰因为无害才没人去检查它对旧数据的影响。

### #9　未训练的价值头 + 认输 = 数据污染

**症状**：正式训练一开跑，黑白胜率就极度失衡。

**根因**：自博弈开了**认输**机制 —— 价值估计低于 `-0.92` 就判负，省下后半盘的算力。
这在成熟模型上是标准做法。但训练最开始时，价值头是**随机初始化**的，
它的输出跟局面毫无关系。于是大量本可以继续的对局被随机地判负，
**训练数据里被灌进了一批错误的胜负标签**。

**怎么确认的**：做了一次受控 A/B —— 同样的种子、同样的配置，只改认输开关。

这里有个我自己的错误值得记下来：确认之前，我已经把"认输导致失衡"这个**未经验证的
因果结论**写进了配置注释。后来去核对 M3 的基准数据，发现那次**也开着认输**，
因果关系并不成立。结论要么改掉，要么做实验 —— 不能因为"听起来很有道理"就写下来。

**修法**：训练初期关闭认输，等价值头有判断力了再开。

### #11　永远开不出白棋局

**症状**：网页版里选"我执白"，点新局，开出来还是黑棋。必现。

**根因**：请求发出前会先 `render()` 一次刷新界面，而 `render()` 里有一句把颜色下拉框
**回写成当前对局的颜色**。等真正去读用户选的值时，"白"已经被覆盖回"黑"了。

```python
guard(fn):
    pending = True
    render()          # ← 这里把 $("color").value 重置了
    setState(await fn())   # ← fn 才去读 $("color").value
```

**根子**：**把一个输入控件当成状态显示去写**。

**为什么没被发现**：服务端 `/api/new {color:"white"}` 的测试一直是通过的。
bug 全在浏览器那一侧，而容器里没有 JS 运行时，前端没有任何自动化覆盖。

**修法**：`render()` 不再碰任何输入控件。另外用纯 Python 的 esprima 做 JS 语法检查
（语法错误的后果是整页白屏，服务端却一切正常），并把"`render()` 里不得给输入控件赋值"
写成静态不变量检查。

**教训**：**覆盖缺口不会因为你没想到就不存在**。这个项目的前端至今没有运行时测试，
这是一个真实存在的空洞，只能靠人工点。

### #15　指标变好，恰恰是因为坏了

**症状**：step 15,600~15,750 这 150 步里，top1 一致率冲到 0.778、价值准确率 0.904、
超出量掉到 0.308 —— **三项全是整个训练的最佳值**。然后一步回落到 0.630 / 0.770 / 0.562，
比出事之前还差。

**根因**：trainer 在 step 15,588 重启，内存里的回放池归零。`min_positions_to_start`
这道门槛是 **50,000 条的绝对值**，而回放池容量是 400 万 —— 于是只攒到 51,326 条
（容量的 1.25%）就开训，网络迅速过拟合那一小撮样本。指标衡量的是"拟合当前池子有多好"，
池子小到 1/80，指标当然好看。

**为什么危险**：这是本章里唯一一个**让指标变好**的 bug。别的至少还表现为"变差"或
"不动"，这个反过来 —— 如果你恰好在那一刻截图、或者用单点最优值写进报告，
就会把一次故障当成突破。（我差点就这么干了，见第 12 章那段更正。）

**怎么防**（已做）：checkpoint 里本来就存着中断前的回放池大小，续训后一比对就知道
恢复得对不对。现在做两件事：恢复量不足一半时**大声告警**（并点明「指标会变好看、极易被误当成进展」）；开训门槛也按中断前池子大小的一半抬高，
宁可等 actor 把池子填回来，也不在被掏空的池子上训练。
（这个现场来自更早的一轮训练，产物已清理，数据是当时记下的。）

### #16　量性能的工具，量的不是生产配置

**症状**：按剖析工具报的单轮耗时推算"一万步要跑 6.8 小时"，实际跑下来是 2.8 小时的速率。
差了 2.2 倍。

**根因**：`scripts/profile_pipeline.py` 剖析的是 `load_model()` 出来的**裸模型**，
而 actor 和 trainer 在生产里都开着 `compile: true`
（`scripts/actor.py` 里那行 `torch.compile(model) if tcfg.compile else model`）。

| | 未编译（工具报的） | 编译后（实际） | 倍数 |
|---|---|---|---|
| trainer 一步 | 0.342 s | 0.137 s | 2.5× |
| actor 一轮 | 83.83 ms | 38.9 ms | 2.2× |

为什么编译能差这么多：这个模型又小又深（4.44M 参数、20 个 block，每个 block 是一串
小算子），batch 2048×225 的张量并不大，**瓶颈是 kernel 启动开销与显存往返而不是浮点量**，
逐元素算子一融就见效。

**怎么发现的**：实测吞吐比推算快一倍多。我当时先给了两个"听起来很有道理"的解释
（同步开销、树还空着导致批量偏大），**都没验证**；去读代码才找到真因，
而且两侧的倍数（2.5× 与 2.2×）能互相印证。

那个 0.137 s 不是另外测的，是**从 `metrics.jsonl` 直接算出来的**：有一段
`train/steps_this_cycle` 恒为 222、`buffer/size` 不变，说明 trainer 在连续训练、
完全没等数据，除一下墙钟差就是纯计算耗时。这正是本轮训练新加的 `wall_time` 字段
第一次派上用场 —— 加它时只想着"别再丢失训练时长"，
没想到它顺带让"算力占比"变成可以事后复算的东西。

**修法**：工具两侧都按 `cfg.compile` 决定是否编译，并在抬头打印当前是开还是关。

**教训**：**一个专门用来测性能的工具，默认测的却不是生产配置** —— 这类错误不会有任何
征兆，只会让人照着错的数字去优化错的地方。另外：**单轮耗时用来看各步骤占比是有效的，
用来推吞吐是无效的**，我两者混用了。

### #17　同一个坑，隔着一整章又踩一次

**症状**：网页版的模型下拉框里，某个模型顶着**另一个模型**的 step 显示。
而且不会自己恢复。

**根因**：渲染候选模型列表时写了这么一句 ——

```js
const active = MODELS.find((m) => m.active);
if (active && S) active.step = S.step;    // render 往数据里写
```

"当前用哪个模型"当时是**服务端全局状态**，`MODELS` 只是某一次请求的快照，
两边短暂不同步是常态。而 `guard()` 在发请求前会先 `render()` 一次 —— 这一写就把
`S.step` 永久写进了错误的那一项。因为是写进数据的脏值而不是每次算出来的，所以刷新都不一定好。

**这就是 #11 的同一个模式**：`render()` 只许读、不许写。#11 当时还专门写了静态不变量测试
挡它 —— 而那条测试只检查了「不得回写 `<select>`/`<input>` 的 `value`」，
**没有覆盖"写回缓存的数据结构"**。测试挡住了症状，没挡住模式。

**修法**分两层：

1. 表层：让"哪个模型在用"和"它练到哪一步"出自**同一份数据**（对局状态里一并下发），
   `render()` 只读。
2. 根子上：把"用哪个模型"从服务端全局状态挪进 `Session`，变成**每局各自持有**。
   两个页面不再互相干扰，这类不一致从结构上就不存在了。同时顺带满足了
   "多局并行、每局用不同模型"的需求。

**教训**：**回归测试写得比 bug 本身窄，就只能挡住那一个 bug，挡不住那一类。**
新的不变量检查现在同时禁止 `render` 系列函数给缓存数据赋值。

顺带记一个我自己的验证失误：第一版端到端验证是"A 局用模型 0、B 局用模型 1，
把 A 切到 1，然后看两边"—— 两边都是 1，我差点当成通过。可 B 本来就是 1，
**这个断言恒为真，和没有断言是一回事**。重做成"两局都从 0 开始、只切一局"才真正验证了独立性。

### #18　续训之后，回放池装的是三分之一个世界

**症状**：换机续训后，策略指标掉了一截（top1 −4pp、超出目标熵 +0.15），
而价值头与威胁头**纹丝不动**。训练照跑，日志没有任何异常。

**根因**：回放池从磁盘分片恢复时，按文件名 `sorted()` 取最新的一批。
分片叫 `actor0_00000123.npz` —— **排序先按 actor 号分组，再按时间**。
于是"取最新的 N 片"取到的是 actor2 的全部、actor1 的一部分、actor0 的**零片**。
四百万条样本的窗口，装进来的是**一个 actor 视角下的世界**。

为什么只有策略头受影响：三个 actor 跑的是同一份权重、同一套超参，
价值与威胁这类"局面事实"在谁的对局里都一样；而策略目标是搜索的访问分布，
它对**开局多样性**很敏感——少了三分之二的探索方向，分布就窄了。
**指标掉得有选择性，这本身就是定位信息。**

**排查里走的弯路**：第一个假设是"续训本身会让 buffer 变陈旧"。
去翻前两次续训 —— 同样的换机、同样的恢复流程，指标**没有跳变**。
假设被证伪，才回头去看这次和前两次有什么不同（分片总数刚刚超过窗口容量，
第一次触发了截断）。**先去找能证伪它的历史数据，比顺着假设往下想省事得多。**

**修法**：按分片序号排序（`_shard_order`），与 actor 号无关。

**验证**（全项目证据强度最高的一次）：同一个 checkpoint、同一批 step、
同一段学习率，**唯一差别是分片装载顺序**，超出目标熵 0.564 → 0.423，
而价值与威胁两种条件下一致。见[附录 A.8](appendix-training-run.md)。

**教训**：**排序键里藏着的分组，是个不报错的过滤器。** 凡是"按名字取最新的 N 个"，
都要先问一句：名字的字典序真的等于时间序吗。

### #19　名字是对的，数字是别人的

**症状**：观战模式一开局，白方 renju15f（实际练了 495 步）在页面上显示
**47,958 步** —— 那是黑方 renju15c 的步数。

**根因**：

```python
def meta_for(self, index: int) -> dict:
    return self._metas.get(index, self._metas[0])   # 没载入就拿 0 号的顶替
```

模型是**按需载入**的（#17 的修法之一：没人选到就不占显存）。观战一开局两边都还没走，
白方还没被载入，`meta_for` 就悄悄返回了第一个模型的元数据。
名字取自 `sources[i]["name"]`（正确），步数取自兜底的 meta（错误），
**两半拼出来的东西看着完全合理**，没有任何地方会报错。

**这是 #17 的第三次**。#17 的表层修法是"名字和步数出自同一份数据"，
根子上的修法是"把模型选择挪进 Session"—— 两条都做了，而**这条兜底路径两条都没覆盖到**：
数据是同一份没错，只是那份数据本身是别人的。

**修法**：`step_of()` 不再顶替。没载入就直接从 checkpoint 文件名读，
和模型清单用的是同一个来源，两处不会各说各话。

**教训**：**`dict.get(k, default)` 里的那个 default，是一句没人会去核对的断言。**
拿"另一个真实对象"当兜底值尤其危险——返回 `None` 会当场炸，返回别人的 meta 只会让页面撒谎。

顺带记一次**验证失效**：修完之后我在跑着的服务上验了一遍，数字对了。
但那个服务跑的还是旧代码 —— 只是白方在我上一次验证时已经被载入，兜底路径压根没走到。
**在没重启的服务上验证一个改动，验的是改动之前的代码。** 重启后才真正验到。

而且这条教训我写下来之后**当场又犯了一次**：两小时后给观战加随机开局，
改完 `server.py` 没重启就说"改好了"，用户刷新页面发现每局还是一模一样。
`server.py` 加载在进程里，改文件不生效；而静态 HTML 是**按 mtime 重读的** ——
所以新滑杆看得见，它发过去的参数却被旧服务端整个忽略。
**"前端变了"恰恰是最容易让人以为"整个改动都生效了"的假信号。**
写进图鉴和做到不是一回事，这一条留在这里当个记号。

## 11.3 四种应对手段

十九个 bug 里没有一个是靠"通读代码"发现的 —— #16 的**真因**确实是读代码找到的，
但前提是先靠实测发现数字对不上，否则根本不会去读那一段。有效的是下面四种做法。

### ① 审计计数器：给不可见的东西装一个指针

凡是"可能悄悄退化"的机制，都给它一个能看见的数字：

| 机制 | 计数器 | 它变成什么样意味着出事了 |
|---|---|---|
| 三三递归判定 | 实际最大深度 / 封顶次数 | 封顶次数 > 0 → 判定退化成近似 |
| Kahan 补偿 | `optim/compensation_norm` | 掉到 0 → 补偿没生效 |
| 数据供给 | `buffer/reuse` | 飙高 → 自博弈跟不上，在过拟合 |
| 分片摄入 | 空闲告警 | 长时间没吃到新数据 → 扫描逻辑坏了 |

**这些计数器要写进验收条件，不是写进日志就完事。** 递归深度那条被写成
"封顶次数必须为 0"，才真正拦住了问题。

### ② 双实现差分：同一个规范，两种做法

规则引擎写了两遍（第 2 章）。同一个人用同一种思路写两遍会犯同样的错，
所以两份实现的**做法必须不同** —— 一份逐格扫描，一份位掩码运算。

再加一条**与实现无关**的性质检查（八重对称不变性），能抓出两份实现都错的情况。

### ③ 对照实验，而不是推理

"认输导致数据污染"这个结论，是靠固定种子的 A/B 实验确认的，不是靠想。
"每请求新线程重建 cuBLAS 句柄"是靠逐层计时确认的，中间还排除了两个听起来很合理的
错误假设。

**听起来有道理的因果，写进文档之前要先做实验。** 否则你会像我一样，
把一个未经验证的结论写进配置注释，几天后才发现它不成立。

### ④ 把发现的每个坑写成回归测试

图鉴里的每一条，现在都有对应的测试或自动检测。这不是仪式感 ——
这类 bug 的特点就是"改对了以后看不出区别"，没有测试，下一次重构就会把它改回去。

举个例子：第 6 章那条"随机落子时禁手告负率必须 > 0"的测试。
它看起来是在测一件废话，实际上它锁住了"禁手点仍是合法落子"这条语义 ——
如果哪天有人顺手在 runner 里加了禁手屏蔽，这条测试会红，而所有别的测试都不会。
